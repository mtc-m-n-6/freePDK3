# ルール

## 原則

| # | 原則 | なぜ重要か |
|---|---|---|
| **1** | **変数・関数・クラスに「意味のある名前」を付ける** | コードを読む人が、処理内容を推測しやすくなるためです。名前を見ただけで「何を表しているか」「何をするものか」が分かれば、コメントや周辺コードを読み込む必要が減ります。 |
| **2** | **1つの関数・処理に1つの責務を持たせる** | 処理が複雑に絡み合うと、コードの理解・テスト・修正が難しくなります。1つの処理を小さく分離すると、「この関数は何をするのか」が明確になり、変更の影響範囲も把握しやすくなります。 |
| **3** | **コードの構造を自然な順序にする** | 「入力 → 処理 → 判定 → 出力」のように、読む人の思考順序に合わせると理解しやすくなります。関数やクラスを適切に並べ、処理が頻繁に前後へ飛ばないようにすることも重要です。 |
| **4** | **条件分岐を複雑にしない** | ネストが深かったり、複数の条件が複雑に組み合わさったりすると、読者が「この条件では何が起きるのか」を頭の中で追跡する必要があります。条件を整理し、例外的なケースを早めに処理することで、主となる処理が見やすくなります。 |
| **5** | **コメントは「何をしているか」より「なぜそうしているか」を書く** | コードそのものを見れば分かる説明は、コードとコメントが食い違う原因になります。一方、「なぜこの処理が必要なのか」「なぜこの方法を選んだのか」はコードだけでは分からないことが多く、将来の保守で非常に役立ちます。 |
| **6** | **重複を減らし、共通処理を適切にまとめる** | 同じ処理が複数箇所に存在すると、仕様変更時に修正漏れが起きやすくなります。ただし、何でも共通化すると逆に抽象化が複雑になるため、「同じ意味・同じ目的の処理」をまとめることがポイントです。 |
| **7** | **Pythonらしい書き方を使い、無理に複雑な書き方をしない** | Pythonには、データの処理や繰り返し、例外処理などを簡潔に表現するための慣用的な書き方があります。これを適度に使うと、Pythonに慣れた人がコードの意図を素早く理解できます。ただし「短く書くこと」自体を目的にせず、可読性を優先します。 |

## 命名規則

| 対象 | ルール |
|---|---|
| モジュール | 小文字＋アンダースコア |
| パッケージ | 小文字 |
| クラス | CapWords（CamelCase ） 方式 |
| 関数 | 小文字＋アンダースコア |
| 変数 | 小文字＋アンダースコア |
| 型変数 | CapWords 方式 |
| 定数 | 大文字 |

# コードチェックリスト

| # | 観点 | 良い状態 | 教材での悪い例（場所） | 確認方法 |
|---|---|---|---|---|
| 1 | 命名 | 変数名をsnake_caseに統一（外部APIの名前は除く） | `imgFile1`（43行）、`imgSize`（5, 79行） | VS Codeの検索（正規表現モード）で `[a-z][A-Z]` を探し、ヒットした名前を確認する。クラス名（CapWords）は正しいので除く |
| 2 | 命名 | 引数の名前が、意味の分かる名前になっている | `ws`、`scale1`/`scale2`、`dx`/`dy`（5行の引数） | 各引数の名前を見て、何かを1文で説明できるか |
| 3 | 重複を減らす | 同じ処理が、繰り返されていない | 画像ファイル名の生成とsaveViewImageの呼び出しが、1用と2用で並ぶ（43〜50行）。imgタグも2行並ぶ（57〜58行） | 数字違いだけの行が並んでいないか。スケールを3つに増やす時、何行足すか数える |
| 4 | 不要なコード | 使われていないimportや、コメントアウトされたコードがない | `import os`（3行）、コメントアウトされたコード（47〜48、123〜124行） | importは `ruff check <ファイル>` で確認。コメントは `#` で始まる行を検索し、コードが入っていないか確認 |
| 5 | 関数の責務 | 1つの関数が、1つの仕事をする。HTMLを組み立てる処理が独立している | `create_magnified_images` が、画像の生成・HTMLの組み立て（22〜66行）・ファイルへの書き出し（68〜69行）を全部している | 関数の仕事を『〜して、〜して』と言った時に、何個の仕事が出てくるか。2つ以上なら分ける対象 |
| 6 | 構造 | テスト用・補助のコードが、本体と分かれている | `DummyWorkspace`（81〜117行）が、本体と同じファイルにある | `DummyWorkspace` が、別ファイルか、実行部の側にあるかを確認する |
| 7 | 直接書かれた数値・文字列・パス | 設定値・パス・ファイル名が、1か所にまとまっている | 出力ファイル名（68行）、設定値（71〜79行）、入力画像のパス（119行）、`width="320"`（57〜58行）、画像ファイル名の形式（43〜44行） | コード中の数値・パス・ファイル名を検索し、設定として分けられているか確認する。出力先を変える時、何か所直すか数える |
| 8 | 実行部の分離 | ファイルをimportしただけで、処理が走らない | 設定・`ws`の生成・関数の呼び出し（71〜121行）が、`if __name__ == "__main__":` で囲まれていない | 作業用フォルダで、このファイルをimportして、何も実行されないことを確認する |
| 9 | コメント・docstringの内容 | 実装と合っている | `ws: The drawing data.`（10行。実際は画像を保存するオブジェクト）、`Assume saveViewImage is a defined function...`（46行。今は`DummyWorkspace`が実装している） | docstringやコメントの各説明を、コードでの実際の使われ方と1つずつ照らし合わせる |
